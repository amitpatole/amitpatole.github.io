cgroupguard

An evidence-based readiness checker for the Kubernetes move from cgroup v1 to cgroup v2. It tells you which nodes are still on cgroup v1 or a hybrid layout, which workloads are likely to break when their node moves, and how many pods that touches — then writes a migration plan you can review.

Status

Pre-1.0. Rules are versioned data with cited sources; runtimes without verified documentation are marked review, never pass or fail. Managed-cloud (GKE, EKS, AKS) plans are generated from provider documentation and have not yet been run on those platforms.

The problem

From Kubernetes 1.35 the kubelet refuses to start on a cgroup v1 node by default, and cgroup v1 support is planned for removal. Moving nodes is easy to schedule and hard to scope: the risk sits in the agents and workloads whose runtimes read cgroup files directly.

How it behaves

  • Read-only by default. It needs no permissions beyond reading nodes, pods and PodDisruptionBudgets, and creates nothing unless you opt in.
  • Never certifies. Output is advisory. Missing evidence is reported as unknown, never as ready.
  • Explains itself. Every finding carries its evidence, why it matters, blast radius, confidence and a primary source.
  • Remediation you can review. fix --plan changes nothing; applying is a separate, confirmed, audited step.

Use it

cgroupguard check --context my-cluster # scan nodes and workloads cgroupguard check --input snapshot.json -o json # scan a saved snapshot cgroupguard fix --plan --context my-cluster # write a runbook, changing nothing

It can also produce Terraform for GKE, EKS and AKS and Ansible for self-managed nodes, export SARIF and CI pipeline files for gating, and run in-cluster as a controller with metrics. Release archives, packages, a container image and a Helm chart are available, with signature verification documented.
